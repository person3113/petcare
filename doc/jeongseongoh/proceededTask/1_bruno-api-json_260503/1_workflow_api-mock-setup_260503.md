### 🛠️ Phase 2: 백엔드 정제 API (Clean DTO) 설계
지저분한 공공 데이터를 프론트엔드에서 즉시 사용할 수 있는 'Basic & Clean' 구조로 변환하는 레이어를 설계합니다.

- [x] **데이터 구조 단순화 (Flattening)**
    - [x] 공공 API의 복잡한 4단계 래퍼(`response.body.items.item`) 제거 로직 설계
- [x] **직관적인 필드 매핑 (Naming & Mapping)**
    - [x] 난해한 필드명 정리 (예: `desertionNo` → `id` 등 별칭 부여)
    - [x] 데이터 타입 단순화 (예: `sexCd: M` → `gender: "수컷"` 등 문자열 변환)
    - [x] **이미지 배열화:** `popfile1, 2...`를 개별 필드가 아닌 `images: []` 배열로 묶어 제공
- [x] **특수 가공 로직 설계**
    - [x] 주소 기반 좌표 정제(Geocoding) 필요 여부 결정
    - [x] 서버 측 캐싱 전략 수립 (지역 코드 및 보호소 목록)

```text
  2. ERD와의 충돌 여부 (계층 분리)
  매우 예리한 지적이십니다! 하지만 충돌이 아니라 '역할 분담'으로 보시면 됩니다.
   - ERD (ANIMALS 테이블): 공공 API에서 데이터를 긁어와서 저장(Sync)할 때는 필드명이 같아야 개발이
     편합니다. 그래서 desertion_no, sex_cd 등 공공 API 명칭을 그대로 씁니다.

     방식을 유지하는 것은 데이터 정합성 측면에서 오히려 안전합니다.
```
